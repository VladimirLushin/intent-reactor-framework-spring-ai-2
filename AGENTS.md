# AGENTS.md

IntentReactor: multi-module Maven (Java 21, bytecode target 21) framework/library that adds LLM intent analysis and ReACT-style planning to Spring Boot 4 / Spring AI 2.0 apps (`com.intentreactor:*` on Maven Central). Tested against Spring Boot 4.0.8 / Spring AI 2.0.1 / Jackson 3 (`tools.jackson`). The project is bilingual: README and user-facing text are mirrored in English (`README.md`, `docs/`) and Russian (`README-ru.md`, `docs-ru/`) — change both, plus the matching prompt-template pairs (below).

## Commands

- No Maven wrapper (`mvnw`) is checked in — system `mvn` + JDK 21 required. (This dev machine runs Temurin JDK 25 with Maven 3.9.16 installed under `~/tools` and `JAVA_HOME` set; the build targets bytecode 21, so a JDK 21+ is sufficient.)
- Full build + tests: `mvn test` from the root reactor.
- One module or one test: `mvn -pl <module> -am -Dtest=ClassName test` (`-am` builds inter-module deps; many modules depend on `intent-reactor-api`/`-core`). Without `-am`, a stale locally installed api/core jar may be used — ALWAYS pass `-am`.
- All tests are pure unit tests: the LLM is always a Mockito-mocked Spring AI `ChatClient`, tools/providers mocked — no API keys, no network. `@JdbcTest` slices use an embedded DB from the test classpath. The one exception is the opt-in live test suite — one `*EndToEndIT` per planning strategy (core: `LiveLlmEndToEndIT`/react, `ReflexionEndToEndIT`, `LatsEndToEndIT`; strategies: 16 classes in `com.intentreactor.strategies.live`, e.g. `CotEndToEndIT`, `SandEndToEndIT`). Each boots the full auto-configuration against a real OpenAI-compatible model; the canonical two-turn calculator scenario + LLM/session properties live in the abstract `LiveLlmEndToEndITBase` (one copy per module). All of them are excluded from `mvn test`/CI by the `*IT` suffix and additionally skip themselves when `LLM_API_KEY` is unset:
  - Single: `$env:LLM_API_KEY='sk-...'; mvn -pl <module> -am -Dtest=<Class> -Dsurefire.failIfNoSpecifiedTests=false test`
  - All core (react/reflexion/lats): `mvn -pl intent-reactor-core -am -Dtest='*EndToEndIT' -Dsurefire.failIfNoSpecifiedTests=false test`
  - All strategies (16; with `-am` the core live tests run first too): `mvn -pl intent-reactor-strategies -am -Dtest='*EndToEndIT' -Dsurefire.failIfNoSpecifiedTests=false test`
  - Endpoint/model defaults are DeepSeek (`deepseek-chat`); overridable via `-Dlive.llm.base-url=` / `-Dlive.llm.model=`.
- Release (CI-only): pushing a `v*` tag runs `.github/workflows/release.yml` — `versions:set` from the tag, `mvn test`, then `mvn clean deploy -Prelease` (flatten + sources + javadoc + GPG + Central publishing), then attaches all `target/*.jar` to a GitHub Release. Keep the version in the README dependency snippets in sync.

## Module map

- `intent-reactor-api` — public contracts only: `Tool`, `Planner`, `IntentPreprocessor`, DTOs (incl. `SessionState`), events (`com.intentreactor.api`). Deliberately no Spring Boot: only `spring-context` + Jackson. New public API belongs here; do not let it depend on other modules.
- `intent-reactor-core` — implementations + main auto-configuration: `IntentReactorAutoConfiguration`, `IntentReactorProperties` (prefix `intent-reactor`). Home of `DefaultReACTPlanner`, `ReflexionPlanner`, `LATSPlanner` (+ search trees in `planner/search/`), `IntentReactorServiceImpl`, and the session persistence layer (`com.intentreactor.core.session`): the `SessionStateStore` facade plus the `FileSystemSessionRepository` fallback.
- `intent-reactor-spring-boot-starter` — thin aggregator: core + optional `mcp-client`/`mcp-server`.
- `intent-reactor-strategies` — extra planners; strategy is chosen purely by property `intent-reactor.planning.strategy`. Each bean in `StrategiesAutoConfiguration` carries `@ConditionalOnProperty(havingValue = "...")` and many wrap `DefaultReACTPlanner` as a delegate. To add a strategy: new `Planner` impl + conditional bean method + README/docs updates (EN + RU).
- Optional add-ons, each with its own auto-configuration: `tool-commons` (`com.intentreactor.tools`), `tool-dynamic` (`com.intentreactor.tools.dynamic` — Rhino JS sandbox), `rag`, `mcp-client`, `mcp-server`, `sand-train` (exports SAND deliberation logs as JSONL; only meaningful with `strategy=sand`).

Package roots differ per module (`core.*`, `strategies.*`, `tools.*`, `sandtrain`) — match the module you edit, not a global scheme.

## Gotchas

- **Default prompts are Russian.** Every built-in prompt template exists in an EN/`-ru` pair (core: `intent-reactor-core/src/main/resources/prompts/`; strategies: `.../prompts/strategies/`). The code defaults in `IntentReactorProperties.PromptResources` point to the **`-ru`** files (e.g. `default-system-ru.md`), while most strategies defaults in `StrategiesProperties.PromptsConfig` point to English files (SAND defaults are `-ru`). Overrides: `intent-reactor.llm.prompt-resources.*` and `intent-reactor.planning.strategies.prompts.*`. When adding a template, add both language variants.
- **Prompt text is a parser contract.** `DefaultReACTPlanner` parses LLM output as JSON with keys `done`/`failed`/`toolName` (`LlmResponseParser`); tool results/errors are appended to history as SYSTEM messages prefixed `[TOOL_RESULT]`/`[TOOL_ERROR]`; there is a format-correction retry loop (`react-format-correction`). Keep markers/keys in sync when rewording templates.
- **Session persistence wraps spring-ai-session** — `org.springaicommunity:spring-ai-session` 0.8.0, managed by the `spring-ai-session-bom` imported in the root pom. The engine saves/loads sessions through the `SessionStateStore` facade over the `org.springframework.ai.session.SessionRepository` SPI. `intent-reactor.session.store` selects one of two `@ConditionalOnMissingBean(SessionRepository.class)` fallbacks: `in-memory` (spring-ai-session's `InMemorySessionRepository`, the default) or `filesystem` (our `FileSystemSessionRepository`; one JSON file per session under `intent-reactor.session.filesystem.path`). Any external `SessionRepository` bean — your own or one auto-configured by the spring-ai-session JDBC starter — automatically overrides both; custom stores implement that SPI, there is no IntentReactor storage interface anymore. A file-backed save is two atomic file rewrites (session header, then batched events) — a crash between them may drop the last dialog step on next load; events stay append-only so nothing corrupts. `IntentReactorAutoConfiguration` carries `@AutoConfigureAfter(name = "org.springaicommunity.session.jdbc.autoconfigure.JdbcSessionRepositoryAutoConfiguration")` (name-based, no compile dep): their JDBC bean is a bare `@ConditionalOnMissingBean` (derived from return type), so ours must be parsed later or two `SessionRepository` beans would be registered.
- **Session state is Jackson 3-serialized** (`tools.jackson`: `SessionState`, messages, `LocalDateTime` fields). Jackson 3 databind handles `java.time` natively, so no `JavaTimeModule` registration is needed or done. History maps to append-only `SessionEvent`s; `planState` + attributes travel as a nested map under `Session.metadata["com.intentreactor.state"]`. Serializing repositories write plain JSON (core's `FileSystemSessionRepository` uses the auto-configured `ObjectMapper`); `SessionStateStore` rehydrates the typed parts on load (`planState`, attributes `multiIntentState`/`originalIntent`/`searchTree`).
- **Session attribute keys are split** across `api.SessionAttributeKeys` (shared/framework-level, e.g. `_pinNextUserMessage`), `core.service.CoreSessionKeys` (confirmation flow: `pendingStep`, `pendingModifiedParameters`, `confirmationRequestedAt`, `originalIntent`, `thoughts`), and `strategies.config.StrategySessionKeys` (per-strategy state). Keys shared across modules must live in `api`; the sand-train module reads the literal `"sand_training_log"` attribute written by `SANDPlanner`. `SessionState` remains the public session contract in `api` — only the persistence layer changed in 0.2.0.
- `intent-reactor-ui-testing-*` entries in the parent `dependencyManagement` and some javadoc comments refer to a **private companion app**, not modules in this repo — leave them alone.
- Cross-module auto-config ordering precedent: `tool-dynamic` depends on core with `provided` scope and uses `@AutoConfigureBefore(IntentReactorAutoConfiguration.class)`.
- Javadoc comments referencing "CLAUDE.md" are stale; the configuration reference lives in README / `docs/13-configuration-reference.md`. Detailed per-topic guides: `docs/01..13` + `docs/strategies/` (SAND is implemented but not yet in README/docs strategy tables).
